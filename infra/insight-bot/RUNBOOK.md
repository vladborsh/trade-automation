# insight-bot — рабочая инструкция (RUNBOOK)

Простыми словами: что где лежит, как выкатить новую версию, как прочитать состояние,
как восстановить базу из резервной копии и что делать, когда приходит тревога от сторожа.

> **Статус на 2026-09-28: в AWS ещё ничего не создано.** Все файлы в `infra/insight-bot/` —
> это описание будущей машины, которое ждёт разрешения пользователя. Никакие ресурсы
> (сервер, бакет, ECR, параметры) не созданы, деньги не тратятся.

---

## 1. Что из чего состоит

| Что | Где | Зачем |
|---|---|---|
| Сервер | EC2 `t4g.micro` (1 ГБ + 2 ГБ swap), регион `ap-northeast-1` (Токио), диск gp3 50 ГБ | на нём круглосуточно работает бот; размеры выбраны под потолок 20 $/мес — см. `COST-PLAN.md` |
| Контейнеры | `postgres:16-alpine` + `insight-bot` + `cloudflared`, запускает `docker compose` | база данных, само приложение и туннель, через который сайт виден из интернета (§11) |
| Секреты | AWS SSM Parameter Store, префикс `/insight-bot` | токены и пароли; в репозитории их нет |
| Резервные копии | S3 `vb-insight-bot-backups-apne1`, папка `pg_dump/`, хранение 35 дней | ежедневный дамп базы в 01:00 UTC |
| Образ приложения | **GHCR** (`ghcr.io/<owner>/insight-bot`) | собирается в GitHub Actions под arm64; ECR не используется — он платный за хранение |
| Доступ на сервер | **только** AWS SSM Session Manager | входящих портов нет вообще, SSH-ключей нет |
| Адрес сайта | домен владельца → Cloudflare Tunnel → `insight-bot:3005` | участники открывают `https://<домен>`; туннель сам звонит наружу в Cloudflare, поэтому входящие порты по-прежнему закрыты |

Файлы на сервере лежат в `/opt/insight-bot/`: `docker-compose.yml`, `.env` (только для root),
`cloudflared.env` (только для root: в нём один токен туннеля, приложение его не видит),
`deploy.sh`, `backup.sh`, `restore.sh`, папка с данными базы `pgdata/`.

## 2. Как войти на сервер

Нужен установленный AWS CLI и права в аккаунте.

```bash
aws ssm start-session --target <instance-id> --region ap-northeast-1
sudo -i
cd /opt/insight-bot
```

`<instance-id>` показывает Terraform (`terraform output instance_id`).

## 3. Как выкатить новую версию (деплой)

Обычный путь — через GitHub Actions:

1. Открыть в GitHub вкладку **Actions** → workflow **insight-bot deploy** → **Run workflow**.
2. Он соберёт образ под arm64, положит его в ECR и запустит на сервере `deploy.sh`.
3. В конце job печатает вывод с сервера. Успех — строка `deploy.sh: healthy on …`.

Руками (если Actions недоступен), уже находясь на сервере:

```bash
/opt/insight-bot/deploy.sh latest      # или конкретный тег: sha-9f2c1ab
```

`deploy.sh` делает по порядку: собирает `.env` из секретов SSM, логинится в ECR,
скачивает образ, поднимает контейнеры, ждёт ответа `/health` до 150 секунд.

**Откат:** тот же скрипт с предыдущим тегом, например `deploy.sh sha-<прошлый коммит>`.
Список тегов: `aws ecr list-images --repository-name insight-bot --region ap-northeast-1`.

## 4. Секреты: создать, посмотреть список, поменять

Значения секретов задаёт пользователь. Terraform их **не создаёт** специально —
чтобы секрет не попал ни в репозиторий, ни в состояние Terraform.

Создать или обновить (пример):

```bash
aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
  --name /insight-bot/TELEGRAM_BOT_TOKEN --value '<токен>'
```

Что нужно заполнить до первого запуска:

| Имя параметра | Что это |
|---|---|
| `/insight-bot/POSTGRES_PASSWORD` | пароль базы (его же использует строка подключения) |
| `/insight-bot/TELEGRAM_BOT_TOKEN` | токен бота, выдаёт @BotFather |
| `/insight-bot/TELEGRAM_SERVICE_CHAT_ID` | id служебного чата: туда идут тревоги и утренний отчёт |
| `/insight-bot/ADMIN_TG_USER_ID` | Telegram id администратора |
| `/insight-bot/TELEGRAM_BOT_USERNAME` | имя продового бота без `@` — по нему кнопка «Log in with Telegram» понимает, какой бот её подписывает |
| `/insight-bot/WEB_BASE_URL` | адрес сайта: `https://<домен>` (без `/` в конце). Без него бот не выдаёт ссылки для входа |
| `/insight-bot/WEB_COOKIE_SECURE` | `true` — cookie входа ходит только по https |
| `/insight-bot/CF_TUNNEL_TOKEN` | токен туннеля Cloudflare (§11, шаг 2). **В `.env` приложения не попадает:** `render-env.sh` кладёт его отдельно в `cloudflared.env` |
| `/insight-bot/WEB_PUSH_VAPID_PUBLIC`, `…_PRIVATE`, `…_SUBJECT` | ключи для push-уведомлений в браузере (§11, шаг 5). Все три вместе или ни одного — иначе приложение не запустится |

`WEB_BASE_URL` и `WEB_COOKIE_SECURE` — не секреты, но лежат там же, чтобы у сервера был один
источник настроек.

Посмотреть, какие параметры есть (**значения не печатаются**):

```bash
aws ssm get-parameters-by-path --path /insight-bot --region ap-northeast-1 \
  --query 'Parameters[].Name' --output text
```

**Смена токена (ротация):** обновить параметр командой выше, затем на сервере
`/opt/insight-bot/deploy.sh latest` — он заново соберёт `.env` и перезапустит контейнер.
Файл `.env` читается только root (права 0600), в образ он не попадает.

## 5. Как прочитать `/health`

Входящих портов нет, поэтому порт пробрасывается через SSM на свой компьютер:

```bash
aws ssm start-session --target <instance-id> --region ap-northeast-1 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["3005"],"localPortNumber":["3005"]}'
# в другом окне:
curl -s localhost:3005/health | jq
```

Что означают поля:

- `streams[].lastMessageAgeSec` — сколько секунд назад по этому потоку приходило сообщение.
  Норма — единицы секунд. Больше 180 — поток молчит, придёт тревога.
- `streams[].reconnects24h` — сколько раз переподключались за сутки. Несколько раз в день — норма
  (биржа сама разрывает соединение раз в 24 часа).
- `streams[].gapsOpen` — сколько пропусков ещё не закрыто дозагрузкой.
- `db.lagSec` — насколько свежая последняя записанная строка.
- `budget.binanceWeightUsed1m` — сколько «веса» запросов к Binance израсходовано за минуту
  (лимит биржи 2400; в обычной работе у нас около 30).

Если сервер отвечает, но контейнер перезапускается: `docker compose logs -n 200 insight-bot`.

## 6. Резервные копии и восстановление

Копия делается каждый день в 01:00 UTC таймером systemd и кладётся в S3.

```bash
systemctl status insight-bot-backup.timer      # включён ли таймер
systemctl status insight-bot-backup.service    # как прошёл последний запуск
journalctl -u insight-bot-backup.service -n 50 # подробности
/opt/insight-bot/backup.sh                     # сделать копию прямо сейчас
```

Посмотреть, что лежит в бакете, и проверить восстановление **без риска для рабочей базы**:

```bash
/opt/insight-bot/restore.sh                                   # список копий
/opt/insight-bot/restore.sh pg_dump/<файл>.dump --into-check  # учебное восстановление
```

`--into-check` разворачивает копию в отдельную базу `insight_restore_check` и печатает
количество строк по таблицам. Рабочая база при этом не трогается. Это и есть «учение по
восстановлению», которое нужно провести один раз до приёмки.

Настоящее восстановление (**это удалит текущую базу**):

```bash
/opt/insight-bot/restore.sh pg_dump/<файл>.dump --into-live
```

Скрипт остановит бота, пересоздаст базу из копии и запустит бота снова. Он потребует
ввести подтверждение словами.

## 7. Что значит тревога сторожа (watchdog)

Сторож каждые 30 секунд смотрит, когда по каждому потоку приходило последнее сообщение.
Если больше `WATCHDOG_SILENCE_MIN` минут (по умолчанию 3) — в служебный чат приходит одно
сообщение о молчании, а когда поток оживёт — одно сообщение о восстановлении. Повторные
тревоги по одному потоку не чаще раза в 30 минут.

Что делать:

1. Посмотреть `/health` (раздел 5): молчит один поток или все.
2. Один поток — обычно биржа. Подождать пару минут: переподключение автоматическое,
   пропуск дозагрузится, и в отчёте за день он будет виден как закрытый.
3. Все потоки — проблема с сетью или контейнером: `docker compose ps`, `docker compose logs`.
4. Поток молчит дольше 15 минут и не восстанавливается — перезапустить приложение:
   `docker compose restart insight-bot` (данные не теряются: при старте пропуск дозагружается).
5. Если после перезапуска тишина остаётся — это уже вопрос к бирже или к региону,
   сообщить Tech Lead и Архитектору, самостоятельно обходные пути не придумывать.

Чего сторож НЕ присылает (и это правильно, а не поломка):

- поток в режиме «деградации» (работает через REST, потому что сокет молчит) — про него уже
  написано в `/health`, тревога каждые 30 минут только мешала бы;
- опросчики с редким шагом: открытый интерес и лонг/шорт спрашиваются раз в 5 минут,
  календарь — раз в 10. Такой поток считается молчащим только после двух пропущенных своих
  шагов, а не после общих трёх минут.

### Отчёт о пропусках за сутки

Раз в сутки в 00:10 UTC приходит отчёт за прошедшие сутки: сколько минутных свечей ожидалось
и сколько есть, по каждой бирже и монете, каких пятиминутных слотов не хватает и какие
пропуски закрыть не удалось. Четырнадцать чистых отчётов подряд — условие приёмки нулевого
этапа. Каждый отчёт также сохраняется в таблицу `gap_reports` — даже если Telegram недоступен.

Отчёт считается **чистым**, когда нет ни одной недостающей свечи, ни одного пропущенного
слота и ни одной незакрытой тишины дольше порога. Важное: коллектор, запущенный в середине
суток, не «потерял» утро — счёт идёт от его первой записи; край хранения у открытого
интереса тоже не считается пропуском.

Пересобрать отчёт за любой день (например, после дозагрузки):

```bash
docker compose exec insight-bot npm run report -- --day 2026-09-27
```

Строка в `gap_reports` за этот день будет перезаписана. Две оговорки про ручной пересчёт:
за сегодняшний день отчёт считается только до текущего момента (будущие минуты не
«пропущены»), а «Пик нагрузки на Binance» покажет «нет данных» — эту величину знает только
тот процесс, который работал сутки.

## 9. Сколько это стоит

Потолок, заданный пользователем, — **20 $ в месяц на всё**. План уложен в **≈ 16.5 $**:

| Статья | В месяц |
|---|---|
| EC2 `t4g.micro`, круглосуточно | ≈ 7.9 $ |
| Диск gp3 50 ГБ (решение владельца 2026-11-02) | ≈ 4.8 $ |
| Публичный адрес IPv4 (1 шт.) | ≈ 3.7 $ |
| S3 (дампы) и запросы | ≈ 0.2 $ |
| Трафик наружу | 0 $ (в пределах бесплатных 100 ГБ) |
| **Итого** | **≈ 16.5 $** |

Сверх этого — домен, ≈ 10 $ в год (≈ 0.85 $ в месяц), платится регистратору, не AWS. Туннель
Cloudflare на бесплатном тарифе ничего не стоит.

Построчно и с альтернативами — `COST-PLAN.md`. Включено предупреждение AWS Budgets: письмо при
расходе выше **18 $** за месяц (и отдельно — по прогнозу, чтобы узнать заранее).

Что дороже всего можно сделать по ошибке: включить NAT-шлюз (≈ 45 $), взять инстанс побольше без
плана экономии, или оставить старые снапшоты. Ничего из этого в конфигурации нет.

## 10. Чего делать нельзя

- Не открывать входящие порты. Вход только через Session Manager.
- Не класть секреты в репозиторий, в образ или в переменные `docker-compose.yml`.
- Не править `/opt/insight-bot/.env` руками: файл собирается из SSM и будет перезаписан.
- Не удалять папку `/opt/insight-bot/pgdata` — это и есть база.
- Не удалять сервер «просто так». У инстанса включена защита от удаления
  (`disable_api_termination = true`), а его диск при удалении сервера **не** удаляется
  (`delete_on_termination = false`): на этом диске база, а в ней лента ликвидаций, которую биржи
  второй раз не отдают (копия в S3 — только на момент последнего ночного дампа). Если сервер
  действительно нужно удалить: сначала сделать свежий дамп (раздел 6), затем снять защиту
  (`disable_api_termination = false` в `terraform/main.tf`, `tofu apply`, или в консоли EC2:
  Actions → Instance settings → Change termination protection), удалить сервер, и после этого
  отдельно удалить оставшийся диск `insight-bot-root` (EC2 → Volumes), когда он точно больше не
  нужен. Пока такой «осиротевший» диск 50 ГБ существует, он стоит ≈ 4.80 $ в месяц.
- Не «чинить» молчащую биржу обходными путями: это вопрос к Tech Lead и Архитектору.
- Не ставить `cloudflare/cloudflared:latest` и не убирать `--no-autoupdate`: версия туннеля
  закреплена в `compose/docker-compose.yml` и меняется только правкой этого файла.

## 11. Адрес сайта: домен и туннель Cloudflare (делает владелец)

Зачем это: чтобы участник открыл с телефона `https://<домен>` и вошёл, не зная ничего про
сервер. Сервер наружу не открывается: маленькая программа `cloudflared` на нём сама
подключается к Cloudflare и забирает оттуда запросы к вашему домену. Замок https и сертификат
даёт Cloudflare бесплатно.

Ниже `<домен>` — ваш домен, например `example.com`. После каждого шага написано, **как понять,
что шаг получился**. Если признака нет — дальше не идти, а написать Tech Lead, на каком шаге
остановились.

### Шаг 1. Купить домен и подключить его к Cloudflare

1. Зарегистрироваться на `dash.cloudflare.com` (бесплатный тариф Free подходит).
2. Проще всего купить домен прямо там: **Domain Registration → Register Domains** (≈ 10 $ в год).
   Тогда подключать ничего не нужно.
3. Если домен куплен у другого регистратора: в Cloudflare **Add a site** → ввести домен →
   тариф Free. Cloudflare покажет **два адреса name server** (вида `xxx.ns.cloudflare.com`).
   Зайти к своему регистратору и заменить там name servers на эти два. Это и есть «смена NS».
   Изменение расходится от нескольких минут до суток.

**Признак успеха:** в Cloudflare на странице домена статус **Active** (зелёная галочка), а не
«Pending Nameserver Update».

### Шаг 2. Создать туннель и положить его токен в SSM

1. В Cloudflare: **Zero Trust → Networks → Tunnels → Create a tunnel**, тип **Cloudflared**.
2. Имя — `insight-bot`. Нажать **Save tunnel**.
3. На следующем экране Cloudflare предлагает команду установки с длинной строкой после
   `--token` (начинается на `eyJ`). Ничего не устанавливать — нужна только эта строка.
   Скопировать её **целиком**.
4. Положить токен в SSM (с компьютера, где настроен AWS CLI):

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/CF_TUNNEL_TOKEN --value '<токен>'
   ```

5. Выкатить заново, чтобы сервер забрал токен: на сервере `/opt/insight-bot/deploy.sh latest`
   (§3). В выводе должна быть строка `render-env.sh: wrote the tunnel token to /opt/insight-bot/cloudflared.env`.

**Признак успеха:** в Cloudflare у туннеля `insight-bot` статус **Healthy** (не «Inactive» и не
«Down»). На сервере `docker compose logs cloudflared` показывает строки `Registered tunnel
connection`. Если там `no token` или `Unauthorized` — токен скопирован не целиком: повторить
пункты 3–5.

### Шаг 3. Направить домен в туннель

1. В туннеле `insight-bot`: вкладка **Public Hostname → Add a public hostname**.
2. **Subdomain** — оставить пустым (сайт будет на самом домене). **Domain** — выбрать `<домен>`.
   Если хочется адрес вида `insight.<домен>` — вписать `insight` в Subdomain; тогда и
   в шагах 4–5 везде писать `insight.<домен>`.
3. **Service:** тип `HTTP`, URL `insight-bot:3005`. (Это имя контейнера внутри сервера, а не
   адрес в интернете — так и должно быть.)
4. **Save hostname**.
5. В SSM записать адрес сайта и включить защищённый cookie, затем выкатить заново:

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_BASE_URL --value 'https://<домен>'
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_COOKIE_SECURE --value 'true'
   ```

   и на сервере `/opt/insight-bot/deploy.sh latest`.

**Признак успеха:** в браузере `https://<домен>` открывается страница входа дашборда, слева
от адреса замок. `https://<домен>/health` отвечает текстом JSON. Если вместо сайта ошибка
Cloudflare **1033** — туннель не подключён (вернуться к шагу 2); **502** — туннель есть, но
приложение не отвечает (`docker compose ps` на сервере).

### Шаг 4. Сказать Telegram, на каком домене кнопка входа

Без этого кнопка «Log in with Telegram» на странице входа пишет «Bot domain invalid».

1. В Telegram открыть **@BotFather** → `/setdomain` → выбрать **продового** бота (не тестового).
2. Отправить `<домен>` — **без** `https://` и без `/` в конце.
3. Убедиться, что в SSM есть `/insight-bot/TELEGRAM_BOT_USERNAME` с именем этого бота (без `@`).

**Признак успеха:** BotFather отвечает «Success! Domain updated». На `https://<домен>` видна
синяя кнопка «Log in with Telegram», и после нажатия Telegram спрашивает подтверждение входа.

### Шаг 5. Ключи для push-уведомлений (VAPID)

Push в браузере работает только по https, поэтому делается после шагов 1–3.

1. На любом компьютере с Node.js:

   ```bash
   npx web-push generate-vapid-keys
   ```

   Выведет две строки: **Public Key** и **Private Key**.
2. Положить в SSM все три параметра (третий — ваш контактный адрес, его видит служба push):

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_PUBLIC --value '<Public Key>'
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_PRIVATE --value '<Private Key>'
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_SUBJECT --value 'mailto:<ваш email>'
   ```

3. Выкатить заново: `/opt/insight-bot/deploy.sh latest`.
4. Записать здесь, кто сгенерировал ключи: владелец сам или агент с его разрешения
   (дата, кто): `____________________`. Менять ключи без нужды нельзя: после смены все
   подписки на уведомления пропадают, и участникам придётся подписаться заново.

**Признак успеха:** `deploy.sh` заканчивается строкой `healthy on …` (если задать не все три
ключа, приложение не запустится и `deploy.sh` скажет, что `/health` не ответил). На сайте
кнопка «Event alerts: off» после нажатия спрашивает разрешение браузера и становится
«Event alerts: on»; подсказка при наведении говорит «also with the dashboard closed» (это и
значит, что работает push, а не только открытая вкладка). Само уведомление приходит за 15 минут
до ближайшего важного события по USD — отдельной «тестовой» кнопки нет.
