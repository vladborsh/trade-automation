## 2. Как войти на сервер

Нужен установленный AWS CLI и права в аккаунте.

```bash
aws ssm start-session --target <instance-id> --region ap-northeast-1
sudo -i
cd /opt/insight-bot
```

`<instance-id>` показывает Terraform (`terraform output instance_id`).

## 3. Как выкатить новую версию (деплой)

Образ лежит в AWS ECR (репозиторий `insight-bot`, Токио). Тег — всегда `sha-<первые 12 символов
коммита>`, теги неизменяемые, `latest` нет. Какой образ должен работать, записано в параметре SSM
`/insight-bot/IMAGE_TAG`.

**Обычный путь — GitHub Actions:** вкладка **Actions** → workflow **insight-bot deploy** →
**Run workflow** (по умолчанию собирает `master`). Он соберёт образ под arm64, положит в ECR
(если такого тега ещё нет), запишет тег в `/insight-bot/IMAGE_TAG` и запустит на сервере
`deploy.sh`. В конце job печатает вывод с сервера; успех — строка `deploy.sh: healthy on …`.

**Руками, с машины разработчика** (если Actions недоступен), из чистого дерева на нужном коммите:

```bash
infra/insight-bot/scripts/push-image.sh            # собрать из git archive, запушить, записать IMAGE_TAG
aws ssm send-command --region ap-northeast-1 --instance-ids <id> \
  --document-name AWS-RunShellScript --parameters 'commands=["/opt/insight-bot/deploy.sh"]'
```

`deploy.sh` без аргумента берёт тег из `/insight-bot/IMAGE_TAG`; с аргументом
(`deploy.sh sha-<12>`) — этот тег. Тег не вида `sha-…` (в том числе `latest`) он отказывается
запускать. Дальше по порядку: собирает `.env` из SSM, входит в ECR ролью сервера, скачивает образ,
поднимает `postgres` и `insight-bot` (и `cloudflared`, только если есть токен туннеля), ждёт
`/healthz` до 150 секунд.

**Откат:** записать в `/insight-bot/IMAGE_TAG` прошлый тег (или передать его аргументом) и
запустить `deploy.sh`. Список тегов:
`aws ecr describe-images --repository-name insight-bot --region ap-northeast-1 --query 'imageDetails[].imageTags'`.

**Если поменялись файлы сервера** (`compose/docker-compose.yml`, скрипты в `scripts/`, юниты
`systemd/`): OpenTofu их на работающий сервер **не** доставляет. `user_data` выполняется только при
первом запуске, а его изменение остановило бы сервер, поэтому tofu его игнорирует. Доставка —
`infra/insight-bot/scripts/sync-box.sh` (из чистого дерева; коммит записывается в
`/opt/insight-bot/SYNCED-FROM`), затем `deploy.sh`.

### 3а. Наблюдение после выкладки (IB-139)

Раньше после каждой выкладки разработчик 30 минут сам проверял сервер. Теперь это делает скрипт
на сервере, `deploy-watch.py`. Правила те же, что были у человека.

**Как он запускается.** Последний шаг `deploy.sh`, сразу после строки `healthy on …`:
`systemd-run --unit insight-watch-<sha>`. Это отдельная служба systemd. Она живёт дальше сессии
SSM, через которую шла выкладка. Одновременно идёт только одно наблюдение: новая выкладка
останавливает прошлое, и в его файле остаётся вердикт `SUPERSEDED` («вытеснено»).

**Что он проверяет.** 7 замеров: сразу и потом каждые 5 минут, всего 30 минут. В каждом замере:
1. контейнер бота: сколько раз перезапускался, не убит ли из-за памяти (OOM), работает ли;
2. свободная память сервера (MemAvailable), занятая подкачка (swap), память бота и postgres;
3. строки с ошибками в логе бота с момента выкладки: сколько, и первые три;
4. расход лимита Binance в минуту. Берётся из счётчика самого бота (`/metrics` изнутри контейнера).
   К бирже скрипт сам не обращается;
5. цикл OI-сигналов: есть ли строка «oi alerts …» на каждое закрытие 15m/1h/4h внутри окна
   (с запасом 5 минут на задержку цикла). И сходится ли число разосланных сообщений:
   у каждого сигнала получателей не больше, чем подписанных участников; сумма получателей в базе
   равна сумме «sent N» в логе. Отдельной строки лога на каждого получателя у бота нет;
6. `/healthz` снаружи, через Caddy (`https://<адрес сайта>/healthz`);
7. нет ли в логе бота сырого `ib_session=` (страховка от IB-BUG-031);
8. `BUILD_SHA` в контейнере совпадает с выложенным.

**Когда тревога (ALARM).** Это старое правило отката, без изменений:
- свободной памяти меньше 100 МБ **на двух соседних** замерах;
- подкачка больше 500 МБ;
- любой перезапуск бота, OOM или контейнер не работает;
- `/healthz` не отвечает **на двух соседних** замерах;
- хоть одна строка с сырым cookie;
- `BUILD_SHA` не тот;
- сигнал разослан большему числу людей, чем сейчас подписано (`alert_oversend`). Если кто-то
  отписался прямо во время наблюдения, тревога ложная; в сообщении это сказано;
- нет строки «oi alerts …» на закрытие, которое цикл уже должен был проверить (`oi_loop_missing`):
  цикл сигналов остановился или завис. Ждём только закрытия внутри окна плюс 5 минут на задержку,
  поэтому выкладка, которая не захватила закрытие 4h, тревогу не поднимет.

Строки с ошибками в логе (пункт 3), расход лимита (пункт 4) и расхождение «сумма получателей ≠ сумма
sent» (пункт 5) тревогу не поднимают. Они записываются в файл как «предупреждения». Tech Lead читает их,
прежде чем отметить выкладку как чистую.

**Что получается на выходе.**
- `/var/log/insight-watch/<sha>.json` — все замеры и вердикт: `CLEAN`, `ALARM:<причина>` или
  `SUPERSEDED`. Файл перезаписывается после **каждого** замера. Если наблюдение оборвалось
  (перезагрузка, служба убита), видно, до какого замера оно дошло, а вердикта нет.
- `/var/log/insight-watch/<sha>.md` — та же таблица для человека.
- **При тревоге** — сразу одно сообщение владельцу в служебный чат Telegram
  (`TELEGRAM_SERVICE_CHAT_ID`), по одному на каждую причину. В сообщении есть точная команда отката
  (`/opt/insight-bot/deploy.sh sha-<прошлый>`). Прошлый тег `deploy.sh` запоминает **до** того,
  как перезаписывает `.env`.
- **Скрипт никогда не откатывает сам.** Решает Tech Lead. На `CLEAN` сообщений нет.
- Если сама выкладка упала (`deploy.sh` завершился с ошибкой, например `/healthz` не ответил за
  150 с), наблюдение не запускается. Вместо него владельцу уходит одно сообщение о неудачной выкладке
  с командой отката.

Токен бота скрипт читает на сервере из `/opt/insight-bot/.env` и передаёт `curl` через stdin
(`curl -K -`). В командной строке, файлах наблюдения и журнале systemd токена нет.

**Что делает разработчик после выкладки.**
1. Выкладывает и проверяет живые страницы на ширине 1240 и 390, со скриншотами (5–10 минут).
2. Запускает ожидание **в фоне** и возвращается к следующей задаче:
   `infra/insight-bot/scripts/watch-wait.sh sha-<12>`.
   Скрипт раз в 2 минуты читает json через SSM. Код выхода: 0 — `CLEAN`; 1 — тревога (сразу, как
   только она появилась) или `ALARM:watch_lost`, если через 40 минут после выкладки вердикта нет;
   3 — `SUPERSEDED`. Ждать через `pgrep -f` нельзя: такой цикл не заканчивается.
3. Tech Lead отмечает задачу «deployed … watch clean» **только** по вердикту `CLEAN` и указывает путь
   к файлу в коммите задач.

**Посмотреть руками:**
`systemctl status insight-watch-<sha>`, `journalctl -u insight-watch-<sha>`,
`cat /var/log/insight-watch/<sha>.md`.

**Проверки без сервера:** `bash infra/insight-bot/scripts/deploy-watch.test.sh` и
`bash infra/insight-bot/scripts/deploy.test.sh`.

**Нагрузка самого скрипта** (замер на сервере 2026-11-05, один прогон из 3 замеров): до 18 МБ памяти
у самого скрипта и до 30 МБ у его дочерних команд (`docker`, `curl`), до 4 секунд и около 0,4 секунды
процессора на замер. Служба ограничена `MemoryMax=128M`.

## 4. Секреты: создать, посмотреть список, поменять

Значения секретов задаёт пользователь. Terraform их **не создаёт** специально —
чтобы секрет не попал ни в репозиторий, ни в состояние Terraform.

Создать или обновить (пример):

```bash
aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
  --name /insight-bot/TELEGRAM_BOT_TOKEN --value '<токен>'
```

Что нужно заполнить до первого запуска:

| Имя параметра | Что это |
|---|---|
| `/insight-bot/POSTGRES_PASSWORD` | пароль базы (его же использует строка подключения) |
| `/insight-bot/TELEGRAM_BOT_TOKEN` | токен бота, выдаёт @BotFather |
| `/insight-bot/TELEGRAM_SERVICE_CHAT_ID` | id служебного чата: туда идут тревоги сторожа, только если `OPS_TELEGRAM_ALERTS=true` (по умолчанию выключено) |
| `/insight-bot/ADMIN_TG_USER_ID` | Telegram id администратора |
| `/insight-bot/TELEGRAM_BOT_USERNAME` | имя продового бота без `@` — страница входа подсказывает, какому боту написать `/password` |
| `/insight-bot/WEB_BASE_URL` | адрес сайта, `https://35-74-48-140.sslip.io` (без `/` в конце). **Пишет OpenTofu** (`web.tf`), руками не менять. Без него бот не выдаёт ссылки для установки пароля (`/password`) |
| `/insight-bot/SITE_ADDRESS` | имя сайта для Caddy, `35-74-48-140.sslip.io`. **Пишет OpenTofu.** В `.env` приложения не попадает: `render-env.sh` кладёт его в `caddy.env` |
| `/insight-bot/IMAGE_TAG` | какой образ запускать, `sha-<12>` (§3). Пишут `push-image.sh` и GitHub Actions |
| `/insight-bot/WEB_COOKIE_SECURE` | `true` — cookie входа ходит только по https. **Пишет OpenTofu** |
| `/insight-bot/CLIENT_IP_HEADER` | `x-real-ip` — из какого заголовка брать адрес посетителя для защиты от подбора пароля и журнала входов. Caddy этот заголовок **перезаписывает**, поэтому посетитель не может его подделать. Без параметра берётся адрес соединения (на сервере это был бы адрес Caddy — все посетители выглядели бы одним). **Пишет OpenTofu** |
| `/insight-bot/CF_TUNNEL_TOKEN` | токен туннеля Cloudflare (§12, шаг 2; сейчас не задан и не нужен). **В `.env` приложения не попадает:** `render-env.sh` кладёт его отдельно в `cloudflared.env` |
| `/insight-bot/WEB_PUSH_VAPID_PUBLIC`, `…_PRIVATE`, `…_SUBJECT` | ключи для push-уведомлений в браузере (§12, шаг 5; push сейчас вне приёмки, работает и по sslip.io). Все три вместе или ни одного — иначе приложение не запустится |

`WEB_BASE_URL`, `WEB_COOKIE_SECURE` и `CLIENT_IP_HEADER` — не секреты, но лежат там же, чтобы у сервера был один
источник настроек.

Посмотреть, какие параметры есть (**значения не печатаются**):

```bash
aws ssm get-parameters-by-path --path /insight-bot --region ap-northeast-1 \
  --query 'Parameters[].Name' --output text
```

**Смена токена (ротация):** обновить параметр командой выше, затем на сервере
`/opt/insight-bot/deploy.sh` — он заново соберёт `.env` и перезапустит контейнер.
Файл `.env` читается только root (права 0600), в образ он не попадает.

## 5. Проверка «живо ли приложение» (`/healthz`) и где смотреть состояние потоков

**`/healthz`** — служебная проверка «приложение живо». Она отвечает ровно `{"status":"ok"}` и
больше ничего: ни потоков, ни нагрузки на биржу. Её читают `deploy.sh` после выката и сам Docker
(healthcheck контейнера). Её можно открыть и снаружи: `https://35-74-48-140.sslip.io/healthz`.

**`/health`** — это уже не служебный адрес, а страница дашборда **Health** (в меню она есть
только у администратора). Перезагрузка этой страницы открывает дашборд, а не JSON. Именно на ней
видно состояние потоков: когда по каждому потоку приходило последнее сообщение, переподключения,
открытые пропуски, работа ликвидационных потоков за 24 часа и 7 дней и нагрузка на Binance. Те же
данные отдаёт `/api/web/health/streams`, тоже только администратору.

**`/metrics`** (счётчики для Prometheus) снаружи всегда отвечает 404. Его закрывают два слоя:
Caddy и само приложение. Приложение отвечает 404 на любой запрос с заголовком `x-real-ip`, а Caddy
ставит этот заголовок каждому запросу извне. Порт приложения 3005 не опубликован даже на самом
сервере, поэтому `/metrics` читается только на сервере, изнутри контейнера:

```bash
aws ssm start-session --target i-002c057dfb439ca24 --region ap-northeast-1
# на сервере:
cd /opt/insight-bot
sudo docker compose exec -T insight-bot node -e \
  'fetch("http://127.0.0.1:3005/healthz").then(r=>r.text()).then(console.log)'   # {"status":"ok"}
sudo docker compose exec -T insight-bot node -e \
  'fetch("http://127.0.0.1:3005/metrics").then(r=>r.text()).then(console.log)'
```

Что смотреть на странице Health:

- «последнее сообщение» по потоку — сколько секунд назад оно приходило. Норма — единицы секунд;
  больше 180 значит, что поток молчит, и сторож это заметит (раздел 7).
- переподключения за сутки. Несколько раз в день — норма: биржа сама разрывает соединение раз
  в 24 часа.
- открытые пропуски — сколько пропусков ещё не закрыто дозагрузкой.
- нагрузка на Binance — сколько «веса» запросов израсходовано за минуту. Лимит биржи 2400, в
  обычной работе у нас около 30.

Если сервер отвечает, но контейнер перезапускается: `docker compose logs -n 200 insight-bot`.

## 6. Резервные копии и восстановление

Копия делается каждый день в 01:00 UTC таймером systemd и кладётся в S3.

```bash
systemctl status insight-bot-backup.timer      # включён ли таймер
systemctl status insight-bot-backup.service    # как прошёл последний запуск
journalctl -u insight-bot-backup.service -n 50 # подробности
/opt/insight-bot/backup.sh                     # сделать копию прямо сейчас
```

Посмотреть, что лежит в бакете, и проверить восстановление **без риска для рабочей базы**:

```bash
/opt/insight-bot/restore.sh                                   # список копий
/opt/insight-bot/restore.sh pg_dump/<файл>.dump --into-check  # учебное восстановление
```

`--into-check` разворачивает копию в отдельную базу `insight_restore_check` и печатает
количество строк по таблицам. Рабочая база при этом не трогается. Это и есть «учение по
восстановлению».

**Проверять копию по содержимому, а не по размеру файла.** Посчитать `count(*)` по главным
таблицам (ликвидации по каждой бирже, `open_interest_5m`, `long_short_5m`, `calendar_events`,
`users`, `schema_migrations`) в рабочей базе прямо перед дампом и в восстановленной — числа должны
совпасть. Так сделано 2026-11-03 (первый дамп 24 МиБ): совпало всё. После проверки удалить
`insight_restore_check` (команду печатает сам скрипт).

Настоящее восстановление (**это удалит текущую базу**):

```bash
/opt/insight-bot/restore.sh pg_dump/<файл>.dump --into-live
```

Скрипт остановит бота, пересоздаст базу из копии и запустит бота снова. Он потребует
ввести подтверждение словами.

## 7. Что значит тревога сторожа (watchdog)

Сторож каждые 30 секунд смотрит, когда по каждому потоку приходило последнее сообщение.
Если больше `WATCHDOG_SILENCE_MIN` минут (по умолчанию 3) — в служебный чат приходит одно
сообщение о молчании, а когда поток оживёт — одно сообщение о восстановлении. Повторные
тревоги по одному потоку не чаще раза в 30 минут.

Что делать:

1. Посмотреть страницу Health в дашборде (раздел 5): молчит один поток или все.
2. Один поток — обычно биржа. Подождать пару минут: переподключение автоматическое,
   пропуск дозагрузится и на странице Health будет виден как закрытый.
3. Все потоки — проблема с сетью или контейнером: `docker compose ps`, `docker compose logs`.
4. Поток молчит дольше 15 минут и не восстанавливается — перезапустить приложение:
   `docker compose restart insight-bot` (данные не теряются: при старте пропуск дозагружается).
5. Если после перезапуска тишина остаётся — это уже вопрос к бирже или к региону,
   сообщить Tech Lead и Архитектору, самостоятельно обходные пути не придумывать.

Чего сторож НЕ присылает (и это правильно, а не поломка):

- поток в режиме «деградации» (работает через REST, потому что сокет молчит) — про него уже
  написано на странице Health, тревога каждые 30 минут только мешала бы;
- опросчики с редким шагом: открытый интерес и лонг/шорт спрашиваются раз в 5 минут,
  календарь — раз в 10. Такой поток считается молчащим только после двух пропущенных своих
  шагов, а не после общих трёх минут.

## 9a. Плановые проверки на сервере (IB-140)

Правило владельца (2026-11-05): никто не ждёт и не опрашивает сервер вручную. Всё, что надо проверить
в определённое время, делает скрипт `checks.py` по таймеру systemd. Он пишет файл с вердиктом.

**Что лежит на сервере** (привозит `sync-box.sh`): `/opt/insight-bot/checks.py`.

**Поставить проверку на время** (через Session Manager / SSM, от root):

    /opt/insight-bot/checks.py schedule v28 '2026-11-05 21:45:00 UTC'
    systemctl list-timers 'insight-check-*'      # таймер виден здесь

Повторный `schedule` той же проверки заменяет прежний таймер. Запустить сейчас, без таймера:
`/opt/insight-bot/checks.py run v28` (с `--dry-run` — ничего не отправляет в Telegram).

**Результат:** `/var/log/insight-checks/<имя>.json` и `.md`, рядом `<имя>.done` — одна строка, вердикт:
- `PASS` — всё в пределах;
- `FLAG:<что>` — проверка прошла, но цифры вне пределов. Это находка: её читает Tech Lead;
- `DEFERRED:<почему>` — прогон истории **не начался**: не хватило свободной памяти на старт (§9b), и так
  все попытки подряд. Ничего не сломано и ничего не записано, владельцу сообщения нет. Поставить заново
  на более тихий час;
- `FAIL:<почему>` — проверка сломалась (запрос упал, данных нет). **Только в этом случае** владельцу
  приходит сообщение в Telegram (тот же путь, что у тревоги после выкладки).

**Ожидание на машине разработчика** — в фоне, по файлу-вердикту, без `pgrep -f`:

    infra/insight-bot/scripts/check-wait.sh v28 <не-раньше-epoch>

Код выхода: 0 PASS, 1 FLAG, 3 DEFERRED, 4 FAIL, 5 нет вердикта к сроку, 2 ошибка AWS.

## 9b. Порог старта для прогонов истории (IB-145)

**Что это.** Программы загрузки истории (сигналы OI, скрытые дивергенции, ликвидации) работают на том же
маленьком сервере, что и живой бот. Перед стартом программа смотрит, сколько свободной памяти
(MemAvailable). Это число берётся уже **после** её собственной загрузки (≈ 66 МБ). Если памяти меньше
порога, программа **не начинает** работу. Это не поломка: результат `DEFERRED`, владельцу сообщения нет.

- **Порог по умолчанию — 170 МБ.** Он зашит в программу и не меняется.
- **На один прогон его можно понизить** флагом `--start-floor N`. Флаг понимают все три скрипта:
  `box-backfill.sh`, `liq-backfill.sh`, `oi-hidden-backfill.sh`. Скрипт передаёт число в программу
  (`docker exec -e MEM_START_FLOOR_MB=N`).
- **Допустимо 140–500.** Ниже 140 скрипт откажется (код выхода 2). Это не переопределяется
  флагом: опустить нижнюю границу можно только решением Tech Lead и коммитом в `history-gate.sh`.
- **Остальная защита не настраивается и остаётся всегда.** Ниже 120 МБ программа встаёт на паузу.
  Через 5 минут такой паузы она останавливается. Ниже 100 МБ скрипт её убивает.

**Что ставят плановые проверки.** `backfill-rerun` и `liq-weekly` всегда просят 140. Причина — замеры
`sar` за 4–5 ноября (раз в 10 минут):
- **с порогом 170** (нужно ≈ 236 МБ свободных до старта) прогон стартовал бы только в 20 % и 61 % замеров;
- **с порогом 140** (нужно ≈ 206 МБ) — в 90 % и 93 %;
- **в 22:00–23:00 UTC**, когда стоит `backfill-rerun`, было 152–239 МБ: со 170 он почти наверняка
  не стартовал бы.

Два прогона ночью 6 ноября шли со 140, и минимум памяти у них был 201 и 170 МБ: до паузы (120) не
дошло.

**Если не хватило памяти.** Проверка повторяет попытку каждые 30 минут, всего 6 попыток (2,5 часа).
- **Ни одна попытка не стартует с 00:55 до 01:30 UTC.** В 01:00 идёт ночной дамп базы
  (`insight-bot-backup.timer`). Попытка, выпавшая на это окно, ждёт до 01:30.
- **Все 6 попыток отказали** → `DEFERRED`. Тогда поставить проверку заново на тихий час:
  `/opt/insight-bot/checks.py schedule <имя> '<дата> <время> UTC'`. Тихие часы по замерам — 02:00–09:00 UTC.

**Когда понижать порог.**
- **Не ниже 140 без решения Tech Lead.** 140 уже согласован (решение TL от 2026-11-06).
- Если и 140 раз за разом даёт `DEFERRED`, это значит, что сервер в покое потерял ещё память. Тогда:
  1. сначала посмотреть, куда она ушла (`sar -r`, память бота и postgres — как в замере после выкладки, §3);
  2. потом спросить Tech Lead.
- **Ниже 140 от отказа никто не защищает: старт сразу у паузы.** Программа начнёт работу при ~140 МБ
  и при собственном росте ещё на ~30 МБ упадёт к паузе (120) уже в первом блоке.

**Проверить, что порог дошёл до программы.** В выводе скрипта есть строка
`== start gate: asked 140, the CLI applied 140`.
- **«applied 170» или «applied old image» при «asked 140»** означает, что на сервере старый образ,
  выложенный до 95366a24: он не знает про порог. Проверка поставит FLAG `start_floor_ignored`.
- **Лечится выкладкой** (§3).

## 10. Чего делать нельзя

- Не открывать другие входящие порты: только 80 и 443 (Caddy), никогда 22 (SSH) и 3005 (само
  приложение). Это закреплено в tofu: `open_web_ports` принимает только 80 и 443. Вход
  оператора — только через Session Manager.
- Не класть секреты в репозиторий, в образ или в переменные `docker-compose.yml`.
- Не править `/opt/insight-bot/.env` руками: файл собирается из SSM и будет перезаписан.
- Не удалять папку `/opt/insight-bot/pgdata` — это и есть база.
- Не удалять сервер «просто так». У инстанса включена защита от удаления
  (`disable_api_termination = true`), а его диск при удалении сервера **не** удаляется
  (`delete_on_termination = false`): на этом диске база, а в ней лента ликвидаций, которую биржи
  второй раз не отдают (копия в S3 — только на момент последнего ночного дампа). Если сервер
  действительно нужно удалить: сначала сделать свежий дамп (раздел 6), затем снять защиту
  (`disable_api_termination = false` в `terraform/main.tf`, `tofu apply`, или в консоли EC2:
  Actions → Instance settings → Change termination protection), удалить сервер, и после этого
  отдельно удалить оставшийся диск `insight-bot-root` (EC2 → Volumes), когда он точно больше не
  нужен. Пока такой «осиротевший» диск 50 ГБ существует, он стоит ≈ 4.80 $ в месяц.
- Не «чинить» молчащую биржу обходными путями: это вопрос к Tech Lead и Архитектору.
- Не ставить `cloudflare/cloudflared:latest` и не убирать `--no-autoupdate`: версия туннеля
  закреплена в `compose/docker-compose.yml` и меняется только правкой этого файла.

дальше входить на `https://35-74-48-140.sslip.io/login`.

1. Имя: `dig +short 35-74-48-140.sslip.io` должен вернуть `35.74.48.140`. Если пусто — сломан

Зачем это: чтобы участник открыл с телефона `https://<домен>` и вошёл, не зная ничего про
сервер. Сервер наружу не открывается: маленькая программа `cloudflared` на нём сама
подключается к Cloudflare и забирает оттуда запросы к вашему домену. Замок https и сертификат
даёт Cloudflare бесплатно.

Ниже `<домен>` — ваш домен, например `example.com`. После каждого шага написано, **как понять,
что шаг получился**. Если признака нет — дальше не идти, а написать Tech Lead, на каком шаге
остановились.

### Шаг 1. Купить домен и подключить его к Cloudflare

1. Зарегистрироваться на `dash.cloudflare.com` (бесплатный тариф Free подходит).
2. Проще всего купить домен прямо там: **Domain Registration → Register Domains** (≈ 10 $ в год).
   Тогда подключать ничего не нужно.
3. Если домен куплен у другого регистратора: в Cloudflare **Add a site** → ввести домен →
   тариф Free. Cloudflare покажет **два адреса name server** (вида `xxx.ns.cloudflare.com`).
   Зайти к своему регистратору и заменить там name servers на эти два. Это и есть «смена NS».
   Изменение расходится от нескольких минут до суток.

**Признак успеха:** в Cloudflare на странице домена статус **Active** (зелёная галочка), а не
«Pending Nameserver Update».

### Шаг 2. Создать туннель и положить его токен в SSM

1. В Cloudflare: **Zero Trust → Networks → Tunnels → Create a tunnel**, тип **Cloudflared**.
2. Имя — `insight-bot`. Нажать **Save tunnel**.
3. На следующем экране Cloudflare предлагает команду установки с длинной строкой после
   `--token` (начинается на `eyJ`). Ничего не устанавливать — нужна только эта строка.
   Скопировать её **целиком**.
4. Положить токен в SSM (с компьютера, где настроен AWS CLI):

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/CF_TUNNEL_TOKEN --value '<токен>'
   ```

5. Выкатить заново, чтобы сервер забрал токен: на сервере `/opt/insight-bot/deploy.sh`
   (§3). В выводе должна быть строка `render-env.sh: wrote the tunnel token to /opt/insight-bot/cloudflared.env`.

**Признак успеха:** в Cloudflare у туннеля `insight-bot` статус **Healthy** (не «Inactive» и не
«Down»). На сервере `docker compose logs cloudflared` показывает строки `Registered tunnel
connection`. Если там `no token` или `Unauthorized` — токен скопирован не целиком: повторить
пункты 3–5.

### Шаг 3. Направить домен в туннель

1. В туннеле `insight-bot`: вкладка **Public Hostname → Add a public hostname**.
2. **Subdomain** — оставить пустым (сайт будет на самом домене). **Domain** — выбрать `<домен>`.
   Если хочется адрес вида `insight.<домен>` — вписать `insight` в Subdomain; тогда и
   в шагах 4–5 везде писать `insight.<домен>`.
3. **Service:** тип `HTTP`, URL `insight-bot:3005`. (Это имя контейнера внутри сервера, а не
   адрес в интернете — так и должно быть.)
4. **Save hostname**.
5. В SSM записать адрес сайта и включить защищённый cookie, затем выкатить заново:

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_BASE_URL --value 'https://<домен>'
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_COOKIE_SECURE --value 'true'
   ```

   и на сервере `/opt/insight-bot/deploy.sh`.

**Признак успеха:** в браузере `https://<домен>` открывается страница входа дашборда, слева
от адреса замок. `https://<домен>/healthz` отвечает `{"status":"ok"}`. Если вместо сайта ошибка
Cloudflare **1033** — туннель не подключён (вернуться к шагу 2); **502** — туннель есть, но
приложение не отвечает (`docker compose ps` на сервере).

### Шаг 4. (Больше не нужен) Домен для кнопки Telegram

С IB-078 на сайт входят по **логину и паролю**, кнопки «Log in with Telegram» больше нет, поэтому
`/setdomain` в @BotFather делать не нужно. Пароль участник задаёт по ссылке из бота: она приходит
сразу после `/start` по приглашению, а позже — по команде `/password` (она же сбрасывает пароль).
Администратору после первого выката тоже нужно один раз написать боту `/password`.

**Признак успеха:** `/password` в боте присылает ссылку `https://<домен>/set-password?t=…`.

### Шаг 5. Ключи для push-уведомлений (VAPID)

Push в браузере работает только по https, поэтому делается после шагов 1–3.

1. На любом компьютере с Node.js:

   ```bash
   npx web-push generate-vapid-keys
   ```

   Выведет две строки: **Public Key** и **Private Key**.
2. Положить в SSM все три параметра (третий — ваш контактный адрес, его видит служба push):

   ```bash
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_PUBLIC --value '<Public Key>'
   aws ssm put-parameter --region ap-northeast-1 --type SecureString --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_PRIVATE --value '<Private Key>'
   aws ssm put-parameter --region ap-northeast-1 --type String --overwrite \
     --name /insight-bot/WEB_PUSH_VAPID_SUBJECT --value 'mailto:<ваш email>'
   ```

3. Выкатить заново: `/opt/insight-bot/deploy.sh`.
4. Записать здесь, кто сгенерировал ключи: владелец сам или агент с его разрешения
   (дата, кто): `____________________`. Менять ключи без нужды нельзя: после смены все
   подписки на уведомления пропадают, и участникам придётся подписаться заново.

**Признак успеха:** `deploy.sh` заканчивается строкой `healthy on …` (если задать не все три
ключа, приложение не запустится и `deploy.sh` скажет, что `/healthz` не ответил). На сайте
кнопка «Event alerts: off» после нажатия спрашивает разрешение браузера и становится
«Event alerts: on»; подсказка при наведении говорит «also with the dashboard closed» (это и
значит, что работает push, а не только открытая вкладка). Само уведомление приходит за 15 минут
до ближайшего важного события по USD — отдельной «тестовой» кнопки нет.
